# ADR-0015: Ревью и публикация привязаны к неизменяемому свидетельству

- Status: Accepted
- Date: 2026-09-24
- Stage: 11.1b, WP-7 (миграция `0069`)
- Уточняет: [ADR-0006](0006-codex-publishing-authority.md) («Publish/deploy
  привязан к immutable git SHA и approval» — теперь это сказано, чем именно)

## Context

Одобрение записывало резюме, id агента-ревьюера и версию задачи — и ничего о том,
*что* одобрено ([0008](../../db/migrations/0008_operator_workflow_actions.sql)).
`project_workspace_states` — периодический снимок, который следующая инспекция
перезаписывает. Поэтому ревью могло быть отличным, а опубликованное дерево —
другим состоянием, и база не могла бы этого показать. В §3.5 было одобрено
изменение с файлом, который не импортируется, при отчёте исполнителя «все тесты
проходят» — дважды ([STAGE_11_2_PREWORK.md](../STAGE_11_2_PREWORK.md) A3).

Решение владельца (2026-09-24, [план](../STAGE_11_1B_PLAN.md) §5): в 11.1b —
только граница. Durable `prepare_publish` и сверка дайджеста; сам push и создание
PR остаются ручным шагом.

## Decision

### 1. Свидетельство — строка, которую никто не меняет

`review_evidence`: одна строка на прогон реализации или ревизии. Пишет её
супервизор, после того как исполнитель отчитался и до того, как завершение
принято, под fencing-токеном прогона (`assert_workspace_fence`). Четыре дайджеста,
все обязательны:

| Поле | Что это |
| --- | --- |
| `base_commit_sha` | коммит, с которого начался **первый** прогон задачи |
| `head_commit_sha` | `HEAD` после прогона |
| `worktree_digest` | дерево, как git его закоммитил бы (§2) |
| `patch_digest` | точные байты патча base → дерево (§3) |

Для репозитория без коммитов (свежий проект — это `git init` и `AGENTS.md`) base и
head — нулевой object id, а патч строится от пустого дерева.

Одного SHA недостаточно: у грязного рабочего каталога коммит не отвечает на
вопрос «что в дереве». Поэтому ранняя формулировка «head SHA **или** tree digest»
отвергнута.

Рядом: прогон и его токен; ограниченный дифф (64 KiB, срез по границе строки),
diffstat и список файлов (до 500), метаданные усечения (`patch_bytes`,
`diff_bytes`, `diff_truncated`, `files_total`, `files_listed`); и **две**
колонки проверок:

- `executor_reported_checks` — что исполнитель сказал о себе. База берёт это из
  его собственного `worker_completion_reports.checks_summary`, а не из того, что
  прислал записывающий;
- `platform_verified_checks` — что платформа проверила сама, не запуская код
  проекта: `patch_reproduces_worktree` (патч, наложенный на base во втором
  scratch-индексе, даёт в точности это дерево) и `worktree_committed` (дерево —
  это дерево head-коммита).

Тесты проекта платформа в 11.1b не запускает. Запуск чужого кода — отдельное
решение о песочнице; до него поле честно говорит, что проверено, а что — заявлено.

`evidence_digest` вычисляет база, не клиент:

```
sha256( "infra-cod-review-evidence-v1" \n run_id \n fencing_token \n
        base_commit_sha \n head_commit_sha \n worktree_digest \n patch_digest )
```

Прогон и токен внутри: одно и то же дерево, сданное двумя прогонами, — два
свидетельства, чем оно и является.

База для прогона не выбирается записывающим: `record_review_base` фиксирует `HEAD`
перед запуском исполнителя, а `record_review_evidence` отвергает свидетельство
относительно любой другой базы (`review_evidence_base_mismatch`). Изменение и
удаление строк свидетельства, баз, доставок и вердиктов отвергаются триггером
(`review_evidence_immutable`).

### 2. `infra-cod-worktree-v1` — канонический алгоритм дайджеста дерева

Реализация — [`review-evidence.mjs`](../../services/runtime-supervisor/review-evidence.mjs).
Изменение алгоритма меняет строку версии.

1. Собственный scratch-индекс (`GIT_INDEX_FILE` в каталоге, созданном для этого
   вычисления): `git read-tree HEAD` (если коммит есть), затем `git add -A -- .`.
   Индекс репозитория не трогается — он принадлежит рантайму. Сначала `HEAD`, чтобы
   отслеживаемый файл, подпадающий под `.gitignore`, остался в дереве.
2. `git ls-files -s -z` по этому индексу: `mode oid stage \t path`.
3. Для записей `160000` — `git status --porcelain=v2 -z --ignore-submodules=none`:
   сабмодуль, в собственном дереве которого есть изменения (`m`) или
   неотслеживаемые файлы (`u`), помечается `+dirty`.
4. Сериализация — байты:

   ```
   "infra-cod-worktree-v1\n"
   "object-format <sha1|sha256>\n"
   для каждой записи в порядке возрастания байтов пути:
     <mode> SP <oid>[+dirty] SP <байты пути> NUL
   ```

5. `worktree_digest = "sha256:" + hex(sha256(сериализация))`.

Как вклад дают перечисленные в плане случаи — и тест на каждый в
[`review-evidence.test.mjs`](../../services/runtime-supervisor/test/review-evidence.test.mjs):

| Случай | Как он входит |
| --- | --- |
| неотслеживаемый файл | запись, добавленная `add -A`; **игнорируемый** — не входит: его не опубликует и push |
| удаление | отсутствие записи, которая есть в `HEAD` |
| mode bits | `100644` или `100755` — исполняемый бит; прочие биты git не хранит и push не переносит, и тест это фиксирует |
| симлинк | `120000` с blob **цели**, не содержимого, на которое он указывает; файл с теми же байтами, что цель, даёт другой дайджест |
| бинарный файл | blob по байтам, как любой другой; патч `--binary` полон |
| сабмодуль | `160000` с checked-out коммитом, `+dirty` при изменениях внутри |
| порядок | сортировка по байтам пути, независимо от порядка вывода |

Путь — байты, не строка: имя файла не обязано быть UTF-8, и дайджест по
«потерявшей» байты расшифровке дал бы двум деревьям один дайджест.

**Что решает git.** Clean-фильтр или eol-преобразование, объявленные в
`.gitattributes` самого репозитория, меняют содержимое, которое git закоммитил
бы, и дайджест — именно этого содержимого: публикуется оно же. Конфигурация
пользователя и системы отключена (`GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM=/dev/null`),
а то, что меняет байты патча или набор файлов, не меняя дерева, закреплено в
командной строке (`core.autocrlf=false`, `core.quotePath=true`, `diff.noprefix=false`,
`diff.renames=false` и др.). Недетерминированный фильтр даст разные дайджесты
одного дерева, и `prepare_publish` откажет — отказ здесь безопасная сторона.

### 3. `infra-cod-patch-v1`

`git diff --cached <base>` по тому же scratch-индексу с закреплёнными опциями:
`--binary --full-index --no-renames --no-ext-diff --no-textconv --no-color
--src-prefix=a/ --dst-prefix=b/ --no-relative --unified=3 --inter-hunk-context=0
--diff-algorithm=myers --indent-heuristic --ignore-submodules=none
--submodule=short -O/dev/null`. `patch_digest` — sha256 точных байтов вывода.
Граница текста диффа на дайджест не влияет (тест).

### 4. git никогда не выполняется от root

Конфигурация репозитория может назвать программы для git (фильтр, fsmonitor). Их
мог записать рантайм, поэтому супервизор запускает git от учётной записи,
которой каталог принадлежит в этот момент (`runuser`, чистое окружение), — не с
бо́льшими правами, чем у рантайма уже были. Scratch-каталог создаётся root'ом,
передаётся этой учётной записи с `0700` и удаляется после.

### 5. Ход ревью получает свидетельство, вердикт ссылается на дайджест

- `deliver_review_evidence` отдаёт ходу ревью свидетельство прогона, о котором
  ход (прогон исходного события — `0059`), и записывает доставку на прогон хода.
  Текст хода содержит четыре дайджеста, diffstat, файлы, дифф и обе колонки
  проверок, подписанные раздельно.
- Вердикт — строка `review_verdicts` со ссылкой `(evidence_id, evidence_digest)`
  одним внешним ключом, поэтому вердикт не может назвать дайджест, которого у
  свидетельства нет.
  - `request_revision` Codex'а — вердикт `changes_requested` на доставленное
    ходу свидетельство; если оно уже не текущее для задачи —
    `review_evidence_stale`.
  - `approve_task_review` — вердикт `approved` на свидетельство последнего
    прогона задачи; без него — `review_evidence_missing`. Событие, аудит и ответ
    несут `evidence_digest`. Панель дайджест не присылает, и это не нужно:
    свидетельство пишется только завершением, которое переводит задачу в
    `awaiting_review`, до версии, которую это завершение создаёт, и к
    завершённому прогону ничего добавить нельзя. «Текущее свидетельство при
    ожидаемой версии» — ровно то, что оператор видел при этой версии.
- Прогон, база которого записана, не может завершиться без свидетельства
  (`finalize_worker_completion` → `review_evidence_missing`).

### 6. Граница публикации — `prepare_publish`

`publish_preparations` — durable-запрос: одобрение создаёт его само; перед ручным
push оператор может попросить ещё раз (`request_publish_preparation`). Супервизор
берёт запрос, в очереди рабочего каталога (никакой смены владельца посередине)
пересчитывает четыре дайджеста от владельца каталога с базой свидетельства и
передаёт их `prepare_publish`, которая:

1. сравнивает все четыре с одобренным свидетельством — любое расхождение
   `review_evidence_digest_moved` с именами разошедшихся полей;
2. отказывает незакоммиченному одобренному дереву — push коммита его не
   перенесёт (`publish_worktree_uncommitted`);
3. отказывает свидетельству, собственная проверка платформы которого не прошла
   (`review_evidence_unverified`);
4. иначе — `prepared` с `head_commit_sha`, событие `publish.prepared` и аудит.

Отказ — исключение, и всё, что записала его транзакция, откатывается. Поэтому
супервизор записывает отказ вторым вызовом (`record_publish_refusal`) с той
причиной, которую нёс отказ; `refusal_reason` — внешний ключ в словарь
`failure_reasons`. Завершённая подготовка неизменна.

Push и PR — ручной шаг: оператор публикует `head_commit_sha` подготовленной строки
по SHA (`git push origin <sha>:refs/heads/<ветка>`), а не текущее состояние
каталога. Publish job, publish intent и квитанции push/PR в 11.1b не строятся.

## Rejected alternatives

- **«Head SHA или tree digest».** Для грязного каталога коммит не описывает
  дерево, а tree digest без head не говорит, что опубликует push.
- **`git write-tree` как дайджест дерева.** Это тот же набор записей, но
  определённый чужим форматом объекта дерева; собственная сериализация задаёт
  порядок и `+dirty` для сабмодуля явно и версионируется вместе с алгоритмом.
  Tree id при этом сохраняется в свидетельстве — для проверки
  `patch_reproduces_worktree`.
- **Дайджест, присланный клиентом.** Тогда он был бы утверждением клиента;
  `evidence_digest` вычисляет база из полей строки.
- **Хранить вердикт как поле задачи.** Задача переживает прогоны; вердикт — факт
  о конкретном свидетельстве.

## Consequences

- Одобрение прогона, запущенного прошлым релизом (базы нет, свидетельства нет),
  отвергается; ревизия записывает свидетельство. Миграция поэтому совместима с
  прошлым релизом ([schema-compatibility.json](../../db/schema-compatibility.json)).
- Каждое завершение реализации стоит одного прохода `git add -A` в
  scratch-индекс и двух `write-tree`; для большого репозитория это секунды.
- `run_checks()` из [RUNTIME_CONTRACT](../RUNTIME_CONTRACT.md) §10 по-прежнему не
  реализован: `platform_verified_checks` — это проверки свидетельства, а не
  тесты проекта.
- Supersedes: ничего.

## Amendment (2026-09-27, Stage 11.4 sprint B P1, migration `0085`)

Push и PR больше не ручной шаг для проектов с репозиторием через GitHub App.
Граница §6 не меняется: публикуется только `head_commit_sha` подготовленной
строки, и только после одобрения оператора.

- **Намерение делает оператор.** `request_publish` (infra_web, проверка владельца)
  создаёт одну строку `publish_intents` на подготовку. Ни модель, ни воркер
  намерение не создают; право `publish.request` (ADR-0017) позволяет агенту лишь
  попросить оператора.
- **Токен — у брокера GitHub, на одну операцию.** Брокер берёт намерение вместе с
  авторизацией на подключение проекта (её ждёт disconnect), минтит токен
  установки на один репозиторий с `contents: write` и `pull_requests: write` и
  отзывает его после. Токен не попадает в argv, базу, события и логи: git
  получает его через `GIT_ASKPASS` из файла `0600` во временном каталоге брокера.
- **git в рабочем каталоге — только от его владельца, не от root (§4).**
  Супервизор выгружает объекты одобренного коммита (`pack-objects --revs`) от
  владельца каталога и отказывает, если `HEAD` сдвинулся после подготовки
  (`publish_head_moved`, с именем ref и тем, где он сейчас). Брокер пушит из
  собственного scratch-репозитория, где нет чужих конфигурации, хуков и фильтров.
- **Push — по id коммита в ветку задачи `infra-cod/<task>`, никогда не force.**
  Ветка с чужими коммитами — отказ GitHub, записанный как `publish_push_rejected`
  с именем ref. PR — против ветки проекта по умолчанию; уже открытый PR для этой
  ветки и есть ответ.
- **Квитанции — события на агрегате намерения:** `publish.requested`,
  `publish.pushed` (ref и коммит), `publish.pull_request_opened` (номер и URL),
  `publish.failed` (причина из словаря), `publish.retried`. Опубликованное
  намерение неизменно. Неудачное оператор повторяет из панели
  (`retry_publish_intent`) — то же намерение, тот же коммит.

Проекты с deploy key и пустые остаются prepare-only (`publish_unsupported_repository`).
