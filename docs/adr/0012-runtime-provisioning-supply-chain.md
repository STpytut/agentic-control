# ADR-0012: Цепочка поставки agent-рантаймов

- Status: Accepted
- Date: 2026-09-14

## Context

Панель установлена и работает, но первая же реальная задача агента падает с
`ENOENT`: `codex` и `opencode` не лежат на runtime PATH. `doctor` честно говорит
об этом с самого начала, и Stage 11.1 закрывает именно этот разрыв.

Вопрос не в том, как поставить бинарь. Вопрос в том, что именно исполняется от
имени `codex-poc` и `opencode-worker` в рабочем каталоге проекта — и чем это
доказывается. План запрещает `curl | sh`, плавающий `latest` и непросмотренные
install-скрипты под root ([STAGE_11_PLAN §11.1](../STAGE_11_PLAN.md)), потому что
каждое из трёх означает «мы не знаем, что установили».

Что выяснено про обе цепочки поставки:

| | Codex | OpenCode |
| --- | --- | --- |
| пакет-обёртка | `@openai/codex` | `opencode-ai` |
| скрипты установки в обёртке | нет | **`postinstall: node ./postinstall.mjs`** |
| где лежит исполняемое | `@openai/codex@<v>-linux-x64` | `opencode-linux-x64@<v>` |
| путь внутри пакета | `package/vendor/x86_64-unknown-linux-musl/bin/codex` | `package/bin/opencode` |
| ответ auth-пробы | `login status` → exit 1 без аккаунта | `auth list` → **exit 0 всегда** |
| скрипты в платформенном пакете | нет | нет |
| `dist.integrity` (sha512) | есть | есть |
| подпись реестра (ECDSA P-256) | есть | есть |
| распакованный размер | 323 МБ | 176 МБ |

Существенно, что настоящий бинарь живёт **не** в том пакете, который принято
устанавливать. Обёртка — это несколько килобайт выбора платформы, а исполняемое
приезжает через `optionalDependencies`. У Codex платформенная сборка выражена
версией того же пакета (`0.154.0-linux-x64`), у OpenCode — отдельным пакетом.

## Decision

### 1. Устанавливается платформенный пакет, а не обёртка

`infra-cod runtime install codex --version 0.154.0` резолвит координаты
платформенной сборки по таблице адаптера и ставит **её**. Обёртка не нужна: её
единственная работа — выбрать платформу, а платформа здесь известна заранее
(`linux-x64` зафиксирован контрактом релиза).

Побочно это снимает вопрос про `postinstall` у `opencode-ai`: скрипт, который мы
не исполняем, не нужно рецензировать. Ни один install-скрипт не выполняется —
ни от root, ни от кого-либо ещё.

### 2. npm не участвует

Ни `npm`, ни `npx`, ни пакетного менеджера на хосте. Реестр используется как
HTTP-источник метаданных и tarball'ов, а распаковка делается тем же закалённым
ридером, который проверяет релизные артефакты: отказ на абсолютных путях, на
`..`, на устройствах и сокетах, список членов читается до записи.

Причина простая: `npm install` — это исполнение произвольного кода с сетевым
доступом от имени того, кто его запустил. Для root на хосте, где стоит панель,
это неприемлемая цена за распаковку tar-архива.

### 3. Подпись проверяется пиннованным ключом, а не полученным по дороге

npm подписывает `dist` каждой версии ECDSA P-256 над строкой
`${name}@${version}:${integrity}`. Ключи публикуются самим реестром — и брать их
оттуда же, откуда приезжает пакет, означает замкнуть круг: кто подменил пакет,
подменит и ключ.

Поэтому публичный ключ реестра пиннуется в дереве (`release/keys/npm-registry.pub`)
ровно так же, как релизный ключ infra-cod, и его смена — рецензируемый коммит.
Порядок проверки повторяет релизный: **подпись → sha512 → безопасный список
членов → распаковка**.

### 4. Точная версия обязательна, диапазоны запрещены

`--version` принимает только точную версию. `latest` не принимается ни в каком
виде — включая «резолвить latest один раз и записать». Хост, на котором
`infra-cod runtime list` показывает версию, должен показывать ту, которую назвал
оператор.

### 4a. Автообновление выключается там, где есть чем, и признаётся там, где нечем

Намерение — чтобы версия менялась только через `infra-cod runtime install ...
--version ...`. Состояние на сегодня разное у двух рантаймов, и это записано, а
не сглажено:

| | механизм | статус |
| --- | --- | --- |
| Codex | `check_for_update_on_startup = false` в `~/.codex/config.toml` | подтверждён в `codex-rs/config/src/config_toml.rs` на теге `rust-v0.154.0` |
| OpenCode | переменная `OPENCODE_DISABLE_AUTOUPDATE=true` в окружении каждого запуска и пробы | подтверждён в `anomalyco/opencode` на теге `v1.18.31` (Stage 12 W1, 2026-09-28): `packages/opencode/src/cli/upgrade.ts`, `packages/core/src/flag/flag.ts`. До W1 — «не подтверждён» |
| Claude Code | `DISABLE_AUTOUPDATER=1`, `DISABLE_UPDATES=1` | подтверждён на хосте для 2.1.270 (`claude update` отказал) |

Первая версия этого файла объявляла переменные окружения
`CODEX_DISABLE_UPDATE_CHECK` и `OPENCODE_DISABLE_AUTOUPDATE`. Обе были
выдуманы для той версии: ни одна не была найдена в исходниках. (`OPENCODE_DISABLE_AUTOUPDATE` позже оказался настоящим — W1 нашёл его в исходниках `v1.18.31`; правило ниже от этого не меняется: сначала источник, потом доверие.) Тест, проверявший, что мы их
передаём, доказывал только то, что мы передаём что-то.

Отсюда правило: адаптер обязан либо назвать источник, по которому контроль
проверен, либо записать, что контроля нет. Второе **останавливает установку**:
рантайм, способный подменить собственный бинарь, делает запись о происхождении
неверной, и согласиться на это может только оператор — флагом
`--accept-unmanaged-updates`, который пишется в `verification.autoUpdate`
(`verified: false`, `acceptedUnmanaged: true`, кем и когда). Первая версия
ограничивалась предупреждением, то есть отказ выглядел как успешная установка.

Непроверенное состояние видно без запроса: колонка `SELF-UPDATE UNMANAGED` в
`runtime list`, проверка `runtime.self_update.<name>` в `doctor`, поля
`self_update_managed` и предупреждение `runtime_self_update_unmanaged` в снимке
здоровья. Пока OpenCode в этом состоянии, его версия может смениться без ведома
оператора — это известный открытый риск, принятый явно.

Содержимое конфигурации не проходит через argv: `/proc/<pid>/cmdline` на
обычном Linux-хосте читают все локальные пользователи, а в `config.toml` лежат
адреса, команды MCP-серверов и всё остальное, что туда положил оператор. Файл
читается и пишется от имени рантайм-пользователя, содержимое идёт через stdin,
результат — `0600`.

Ветка «эта версия уже установлена» проходит те же гейты, что и любая другая:
smoke-тест, обязательную политику самообновления и проверку простоя. Запись
`verified: true` описывает момент, когда она была сделана, — файл с тех пор могли
отредактировать, сбросить или восстановить из бэкапа, снятого до появления
контроля. Гейт обходят не только убрав его, но и оставив дорогу мимо.

Ссылка и `runtimes.json` — одна операция: при неудачной записи ссылка
возвращается на прежнюю версию. SIGKILL между ними это не закрывает; для того и
существует `verify`.

Запись настройки для Codex делается TOML-осознанно. Дописывание строки в конец
файла — ошибка, которая выглядит успехом: если файл заканчивается внутри
таблицы (`[mcp_servers.*]` — обычный случай), настройка становится полем этой
таблицы, Codex её не видит, а `grep` её находит. Настройка ставится в корневую
таблицу, одноимённое поле внутри таблицы не трогается, файл пишется от имени
рантайм-пользователя и перечитывается через ту же границу.

### 5. Дерево исполняемого root-owned и неизменяемо для рантайма

`/opt/infra-cod/runtimes/<name>/<version>/` принадлежит `root:root`; рантайм-
пользователь имеет право исполнять и не имеет права писать. Состояние
аутентификации живёт отдельно, в домашнем каталоге своего пользователя
(`/home/codex-poc/.codex`, `/home/opencode-worker/.config/opencode`), который
создаётся tmpfiles и уже описан unit-контрактом.

Это разделение — то, что делает осмысленной фразу «рантайм не может изменить свою
установку»: доверенное дерево и изменяемое состояние не пересекаются.

### 6. Версия ставится рядом, проверяется и только потом становится активной

Новая версия распаковывается рядом с активной, проходит smoke-тест **от имени
своего Unix-пользователя через тот же `runuser`-барьер, что использует
супервизор**, и лишь затем `/usr/local/bin/<name>` атомарно переключается на неё.
Неудачный smoke оставляет активной прежнюю версию.

Барьер воспроизводится дословно, а не приблизительно:

```
/usr/sbin/runuser -u <user> -- /usr/bin/env -i \
  HOME=<home> PATH=/usr/local/bin:/opt/node/bin:/usr/bin:/bin PWD=<cwd> LANG=C.UTF-8 <command>
```

Проверка бинаря от root — это проверка другого вопроса. Stage 10 закончился
установкой, где `doctor` сообщал о работоспособности того, что рантайм-
пользователь исполнить не мог.

`PWD` в этой строке — переменная окружения; процесс она никуда не переносит.
Рабочий каталог передаётся отдельно и по-настоящему. Отсутствующий домашний
каталог — отказ, а не запасной вариант: fallback отдавал бы дочернему процессу
рабочий каталог вызывающего (root, внутри дерева релиза), продолжая объявлять в
`PWD` домашний каталог рантайма.

Каждая установка получает **собственный неизменяемый каталог**
(`<version>`, затем `<version>+2`, …). Установленное дерево не переписывается и
не переименовывается из-под ссылки, которая его называет: переустановка тех же
байтов — no-op, любая другая — новый каталог и один атомарный перенос символьной
ссылки; старое удаляется только после переключения. Предыдущий вариант двигал
старое дерево в сторону, а новое на его место, и `/usr/local/bin/<name>` на время
двух переименований указывал в никуда — а если машина останавливалась между ними,
то навсегда.

Переключение фехтуется **внутри супервизора**, а не остановкой его unit'а.

Все сессии на хосте запускает один процесс: account-, chat- и catalog-воркеры
ходят к `runtime-supervisor` через сокет и сами ничего не спавнят. Отсюда была
соблазнительная мысль остановить его unit на время переключения — и она неверна.
Unit общий для обоих рантаймов, а его остановка завершает все дочерние каналы:
установка Codex убила бы живую сессию OpenCode, то есть ровно тот вред, ради
предотвращения которого правило и существует. Свою гонку она тоже не закрывает —
сессия, допущенная за мгновение до `stop`, этим же `stop` и убивается.

Поэтому fence стоит там, где принимается решение о допуске, и он **пер-рантайм**:

* `pause` — новые запуски этого рантайма отклоняются с retryable-ошибкой
  («сейчас нельзя» ≠ «так не будет работать никогда»; воркеры их различают);
* установка ждёт, пока счётчик открытых запусков дойдёт до нуля — **ждёт, а не
  убивает**; `--wait <seconds>` задаёт, сколько;
* `resume` возвращает допуск, и его неудача — это неуспешная установка, а не
  предупреждение в логе: хост, на котором нельзя стартовать сессию, не должен
  выглядеть успешно установленным.

Второй рантайм при этом не затрагивается вообще. `pgrep` остаётся — но уже как
вопрос о том, что происходит **вне** супервизора (шелл оператора, процесс,
переживший прошлый сбой), а не как основная защита.

Переключение и запись в inventory защищены durable-файлом
`runtime-switch.<name>.json`, который пишется до `rename` и удаляется после
записи и **несёт в себе ту запись, которую предстояло внести**. Внутрипроцессный
откат закрывает всё, что процесс переживает; SIGKILL он не закрывает. Файл —
вторая половина: `runtime verify` сравнивает цель ссылки с записью и сообщает о
расхождении, `runtime reconcile --apply` дописывает незавершённое переключение
или возвращает ссылку — под тем же fence, что и установка, потому что двигает ту
же ссылку. Утверждение, что reconcile-путём является сам `verify`, было неверным:
он ничего не сравнивал и ничего не исправлял.

Границы durability названы явно. `write` + `rename` атомарен относительно смерти
процесса и ничего не обещает при потере питания: переименование может попасть на
диск раньше байтов, которые оно переименовывает. Поэтому intent-файл, inventory и
каталог, в котором живёт symlink, проходят `fsync` — сначала данные, затем
запись каталога. Содержимое интента при чтении проверяется целиком (schema,
рантайм, версия, каталог, путь ссылки, наличие установки в `installed`): он
читается с диска и используется для записи inventory, поэтому «в нём есть поле
entry» — не основание ему верить.

Архив проверяется **до записи**, по листингу: типы всех записей, цели всех
ссылок, и то, что каждая ссылка указывает на член этого же архива. Проверка после
распаковки опаздывает на один шаг — распаковка и есть создание ссылки. Внутренняя
ссылка «в никуда» тоже отказ: во что она разрешится, решает тот, кто первым
запишет файл по этому пути. Сам исполняемый файл обязан быть обычным файлом, а не
ссылкой на него.

### 7. Состояние — в `/etc/infra-cod/runtimes.json`, и в нём нет секретов

Schema-versioned, root-owned, пишется атомарно. Записывает рантайм, точную
версию, digest, источник, активный путь, OS-пользователя, актора установки и
результат проверки. Учётных данных там нет и быть не может: они живут в домашних
каталогах рантайм-пользователей и никогда не попадают ни в этот файл, ни в
события, ни в снимок здоровья.

### 8. Готовность — четыре независимых состояния

`installed` (проверенный бинарь есть), `authenticated` (у рантайм-пользователя
есть пригодные учётные данные), `capability_verified` (точная связка
рантайм/адаптер/модель/доступ прошла), `ready` (всё перечисленное актуально и
сервисная граница здорова). UI не имеет права их схлопывать: «бинарь стоит» и
«задачу можно запускать» — разные утверждения, и оператор различает их раньше,
чем нажмёт кнопку.

### 9. Две вещи, которые сказал только хост

Обе выяснились при первой установке на VPS, обе — про расхождение между тем, что
адаптер утверждает, и тем, что в пакете лежит.

**Путь к исполняемому у Codex — не `package/bin/codex`.** Платформенный пакет
несёт целое vendor-дерево (сам бинарь, `codex-code-mode-host`, `bwrap`, `rg`,
собранный zsh) под rust-триплетом: `package/vendor/x86_64-unknown-linux-musl/bin/codex`.
Триплет — это **не** npm-строка платформы, и он **musl**, статически слинкованный,
поэтому и работает на glibc-хосте. Установка отказалась по имени
(«the package does not contain package/bin/codex») — ровно то поведение, которое
требуется, но проверить это можно было только у реестра.

Отсюда `scripts/check-runtime-adapters.mjs`: спрашивает у реестра, существует ли
то, что адаптер собирается исполнять. Он ходит в сеть и потому не входит в
офлайновый гейт (`run-suites-in-container.sh` работает с `--network none`);
запускать при изменении координат адаптера и перед релизом с таким изменением.

**`opencode auth list` выходит с кодом 0 при пустом хранилище.** Замерено на
хосте: печатает «0 credentials» и возвращает успех. Вера в код возврата
объявляла бы рантайм без единой учётной записи `authenticated` — зелёным в
панели, допущенным к диспатчу и сломанным на первом же обращении к провайдеру.
Это ровно то схлопывание, против которого и существуют четыре отдельных
состояния.

Поэтому адаптер может назвать **свидетельство**: файл, который обязан
существовать и быть непустым. Проверяется от имени рантайм-пользователя, по коду
возврата `test -s`, и никогда не читается — счётчик был бы безвреден, содержимое
нет, а `test -s` не нужно ни то ни другое. Отсутствие файла — «не
аутентифицирован», то есть отказ в работе: сторона, которая стоит оператору
недоумённой минуты, а не задаче — сорванного запуска. Разбор строки
«0 credentials» ошибался бы в другую сторону при первой же смене формулировки.

У Codex свидетельства нет и не требуется: его `login status` отвечает кодом.

## Consequences

- Установка одного рантайма стоит около 320 МБ (Codex) или 180 МБ (OpenCode)
  распакованными, а staged-версия рядом с активной временно удваивает это. На
  целевом 30-гигабайтном диске (23 ГБ свободно) это приемлемо, но
  `runtime remove --version` становится обязательной частью контракта, а не
  удобством.
- Хост обращается к `registry.npmjs.org` во время установки рантайма. Это
  единственный сетевой источник, кроме релизных артефактов, и он назван явно.
- Смена ключа подписи реестра ломает установку до рецензируемого коммита с новым
  ключом. Это осознанная цена за то, что подпись проверяется чем-то, чему мы
  доверяем заранее.

## Дополнение: Stage 12 W1 (2026-09-28)

- Контроль самообновления OpenCode подтверждён по исходникам закреплённого тега и записан с источником; установка больше не требует `--accept-unmanaged-updates`. Запись, сделанная до W1, остаётся «unmanaged», пока версию не установят заново той же командой — `doctor` называет её.
- При установке записывается SHA-256 исполняемого файла из подписанного пакета (`installed[].executableSha256`); повторная установка той же версии сверяет дерево на диске со свежераспакованным пакетом и отказывает, если они разошлись. `doctor` проверяет хэш активной версии (`runtime.executable_digest.<runtime>`) — третий слой против самообновления, который не зависит от того, работает ли настройка.
- Адаптер объявляет требования к хосту по версиям (`hostRequirements`: `landlock`, `bwrap.userns`); `doctor` проверяет их только чтением (`runtime.host_requirement.<runtime>.<requirement>`). Codex ≥ 0.155.0 требует bubblewrap с пространствами имён — решение R13 в `docs/RUNTIMES_AND_MODELS_DESIGN.md`.
