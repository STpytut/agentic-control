# ADR-0013: Каждый нативный ход — это Run

- Status: Accepted
- Date: 2026-09-16
- Stage: 11.1b, WP-3a (миграция `0059`)

## Context

Модель данных давно говорит, что такое Run: *конкретный turn, resume,
implementation или review*. На деле Run был только у реализации. Ход Codex в
чате и ход ревью были `runtime_jobs` с `run_id NULL`, а воркер передавал
супервизору проект и больше ничего:

```js
// services/control-plane/codex-chat-worker.mjs
const processHandle = await supervisor.openCodexAppServer({ projectId: context.project_id });
```

Из-за этого гонка A1 ([STAGE_11_2_PREWORK.md](../STAGE_11_2_PREWORK.md))
неустранима в текущей форме. Доступ к рабочему каталогу должен быть явным
грантом, привязанным к конкретному ходу (WP-3b, `0060`), а у хода Codex нет
ничего, к чему грант можно привязать.

## Decision

### 1. Каждая попытка оркестраторского хода получает свой Run

`codex_chat_turn` → phase `orchestrator_turn`, `resume_codex` → phase
`review_turn`. Других продюсеров `resume_codex` нет: его порождают только
`implementation.completed` и `revision.completed`. Поэтому «resume» и «ход
ревью» в этой схеме — одна и та же работа, и план, называющий их тремя
случаями, описывает два типа задач.

Run такого хода — `write_capable = false`, агент — оркестратор задачи, сессия —
`task_chat:<task_id>`. На первом ходу сессии ещё нет, её узнают при завершении.

**Одна попытка — один Run.** Retry — это новый ход. Попытка, которую он
заменяет, закрывается, а не переиспользуется, поэтому статус Run описывает один
ход, а не их сумму.

### 2. Run создаёт триггер на `runtime_jobs`, а не функции claim/complete

У задачи Codex шесть путей смены статуса: claim, повторный claim после истёкшей
аренды, завершение, retry, dead-letter, прерывание. Они разнесены по пяти
функциям в четырёх миграциях. Правило, скопированное в каждую, начнёт
расходиться, а седьмой путь, который кто-то добавит, будет тем, что про правило
забудет. Триггер срабатывает на колонки, которыми отмечается попытка
(`status`, `attempt_count`), и только для двух оркестраторских типов.

### 3. Ход оркестратора никогда не бывает `lost`

`lost` в этой схеме значит одно: писатель, у которого истекла аренда рабочего
каталога. Его ставит `reconcile_expired_workspace_locks`, и на него опирается
восстановление замка. `recover_lock` берёт последний `lost` run проекта и
спрашивает, жив ли его процесс. У хода нет `process_ref`, поэтому потерянный ход
ответил бы «процесса нет» за реализацию, которая, возможно, ещё идёт, и каталог
был бы передан из-под неё. Ход с истёкшей арендой — `failed` с
`turn_lease_expired`.

Это правило держит в безопасности и предыдущий релиз: он читает `lost`
по-старому, пока обслуживает новую схему во время обновления.

### 4. Инвариант держит база

`CHECK`: оркестраторская задача, у которой была хотя бы одна попытка, имеет
`run_id`. Прошлые попытки получают Run при миграции. Время берётся из задачи,
статус — из её исхода: `completed` либо `failed` с `backfilled_<статус задачи>`.
Задача без владельца отвергается по имени до записи, без угадывания.

### 5. Читатели, считавшие Run реализацией, исправлены вместе с изменением

Прочитан каждый читатель `task_runs`; список — в
[STAGE_11_1B_ACCEPTANCE.md](../STAGE_11_1B_ACCEPTANCE.md). Изменены четыре:

| Где | Предположение | Что было бы без правки |
| --- | --- | --- |
| `finalize_runtime_interrupt` | `run_id IS NOT NULL` ⇒ прервана реализация | остановка хода Codex пыталась бы подать запрос на ввод без fencing-токена, и всё прерывание откатывалось бы — ход оставался `in_flight` |
| `claim_workspace_operation`, `recover_lock` | последний `lost` run проекта — писатель | подстраховка к правилу 3 там, где предположение сделано |
| супервизор, `manageWorkspace` | то же | то же |
| панель, снапшот задачи | последний run задачи — реализация | статус и сессия реализации подменялись бы ходом чата |

Метрики `runs_*` в health по-прежнему считают только пишущие runs. Ходы
считаются отдельно (`turns_active`, `turns_failed_24h`).

## Rejected alternative

**Отдельный агрегат `workspace_access_grants`, привязанный к `runtime_job`.**
Грант крепился бы к задаче, а не к ходу. Отвергнуто по двум причинам.

1. Задача переживает попытки. После retry грант, выданный первой попытке,
   остаётся действительным для второй, а на вопрос «кто держал доступ в этот
   момент» ответ даёт задача, у которой было три хода. Это ровно та потеря
   истории, из-за которой WP-9c разделяет снимок выбора и журнал попыток.
2. Это вторая модель «хода» рядом с `task_runs`, у которого уже есть статусы,
   fencing-токен, сессия и связь с замком. Реализация и ход Codex описывались
   бы разными сущностями, и каждый читатель выбирал бы, какую из них спрашивать.

## Consequences

- WP-3b привязывает грант к Run — к любому, без различения реализации и хода.
- `runs_*` в health означают то же, что раньше, а ходы видны отдельно.
- Строк в `task_runs` становится больше на число ходов Codex. Индекс активных
  runs не уникальный, поэтому ход и реализация одной задачи сосуществуют.
- Supersedes: ничего. Уточняет термин Run из [DATA_MODEL.md](../DATA_MODEL.md).
