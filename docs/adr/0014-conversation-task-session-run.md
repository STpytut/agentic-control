# ADR-0014: Conversation, Task, NativeSession и Run — четыре разные сущности

- Status: Accepted
- Date: 2026-09-17
- Stage: 11.1b, WP-4 (миграция `0063`)
- Уточняет: [ADR-0013](0013-every-native-turn-is-a-run.md)

## Context

Модель противоречит собственному интерфейсу
([STAGE_11_2_PREWORK.md](../STAGE_11_2_PREWORK.md) A2):

- архитектура говорит, что каждая задача — свой разговор;
- панель собирает один разговор из цепочки follow-up задач, обходя
  `followup_of_task_id` в браузере;
- при follow-up нативный id сессии **копируется** в новую строку
  `agent_sessions`, а индекс родословной не уникален — две ветки могут
  возобновлять одну нативную сессию.

Нативная сессия — это память агента. Два хода, возобновляющие её из разных веток,
портят ровно то, ради чего продукт существует.

Чтение кода и данных хоста перед этим решением добавило две вещи, которых в
prework не было.

**Сессия принадлежит задаче через строку.** Строка `agent_sessions` находится по
`purpose = 'task_chat:<task_id>'` или `'task_executor:<task_id>'`; так её ищут пять
SQL-функций. Поэтому follow-up и вынужден копировать: у новой задачи другой
`purpose`.

**Чат в панели сейчас пуст.** Панель берёт последние 100 событий *проекта* —
события домена и аудита вместе, по `occurred_at` — и фильтрует по родословной
задачи. На хосте аудит — это 1327 `workspace.provisioning_requested` и 1219
`workspace.operation_completed`; из 23 и 2 сообщений чата двух проектов в окно не
попадает **ни одно**. Порядок по времени — не единственная проблема: окно не
разговора, а проекта, и аудит в нём вытесняет разговор.

## Decision

### 1. Четыре сущности

```
Conversation   один пользовательский чат проекта
  ├─ Task       одна единица работы: задача → реализация → ревью
  ├─ NativeSession   каноническая CLI-сессия агента, одна на разговор и роль
  └─ Run        одна попытка хода (ADR-0013)
```

- **Conversation** — новая таблица `conversations`. Разговор создаётся вместе с
  первой задачей; follow-up — следующая задача того же разговора.
- **Task** принадлежит ровно одному разговору (`tasks.conversation_id NOT NULL`).
- **NativeSession** — строка `agent_sessions`, принадлежащая **разговору**, а не
  задаче: колонки `conversation_id` (внешний ключ), `role ∈ {chat, executor}` и
  `agent_id`, и уникальный индекс по `(conversation_id, role, agent_id)` среди
  активных строк. Follow-up находит ту же строку по этим колонкам — копировать
  нечего, и вторая активная сессия того же агента в той же роли физически
  невозможна. `purpose` остаётся описательным полем; ничто не ищет по нему.
  Какая задача какой сессией пользовалась, записано в `task_runs.session_id`: после
  ADR-0013 run есть у каждого хода и каждой реализации.
- **Run** — без изменений, ADR-0013.

### 2. Разговор линеен; ветвления нет

У задачи не больше одного follow-up — уникальный индекс по
`followup_of_task_id`. Это ответ на вопрос «что происходит с нативной сессией при
форке»: **форка нет**. Кто хочет пойти другим путём — начинает новый разговор, и
у нового разговора новые нативные сессии. Возобновить одну нативную сессию из двух
веток становится невозможно на уровне базы, а не на уровне аккуратности кода.

### 3. Идентичность нативной сессии

`agent_sessions.session_namespace text NOT NULL` и уникальность
`(session_namespace, native_session_id)` там, где id есть.

**До 11.4 пространство имён — это тип рантайма.** Нативный id живёт в хранилище
сессий CLI, то есть в home рантайма под его учётными данными. До 11.4 на хосте
ровно одна установка каждого рантайма и одно подключение на неё, так что пара
«установка + слот учётных данных» однозначно задаётся типом рантайма. **После 11.4**
пространство имён становится внешним ключом на границу подключения
(RuntimeInstance, ADR-0010): одна и та же строка id под другим инстансом — другая
сессия, и уникальность это допускает.

### 4. Порядок разговора: где живёт счётчик

- **Счётчик** — `conversations.last_sequence bigint`.
- **Номер** получает событие домена: `domain_events.conversation_id` и
  `domain_events.conversation_sequence`, уникальные вместе.
- **Выдаётся триггером `BEFORE INSERT` на `domain_events`**, в той же транзакции,
  что и вставка события, через `UPDATE conversations SET last_sequence = last_sequence + 1
  RETURNING`. Сначала номер планировался внутри `append_event`: все *функции* пишут
  события через неё. Но первый прогон тестов нашёл четыре фикстуры, вставляющие
  события задач напрямую, — а номер, который выдаёт одна функция, пропускает любой
  другой путь вставки. Триггер выводит обе колонки сам и игнорирует переданные, так
  что номер нельзя ни пропустить, ни подделать. Блокировка
  строки разговора упорядочивает одновременных писателей: номер растёт монотонно и
  без дыр среди закоммиченных событий, потому что откаченная транзакция откатывает
  и приращение.
- **События без задачи** (уровня проекта) номера не получают: они не часть
  разговора.

**Двум агентам — один порядок.** Номер разговора общий для Codex, OpenCode и
оператора: разговор — это проекция нескольких сессий, и порядок у проекции один.
Собственный порядок каждого агента остаётся внутри его нативной сессии.

**Нативные события рантайма номеров разговора не тратят.** У них уже есть своя
последовательность — `runtime_activity_events UNIQUE(job_id, sequence)` — и попытки
внутри задачи различаются по `run_id` (ADR-0013). Это ровно «отдельная
последовательность для нативных событий», которую требует план; новой не нужно.

### 5. Аудит не входит в порядок разговора

Разговор упорядочен только событиями домена. Аудит остаётся в своём представлении,
по времени.

## Rejected alternatives

**Таблица связи `task_sessions(task_id, role, session_id)`**, как предлагал план.
Надёжна — внешние ключи, первичный ключ на связь — но это второй источник правды
для факта, который уже записан: `task_runs.session_id` связывает с сессией каждый
ход и каждую реализацию. Два места, которые должны совпадать, со временем
расходятся, а поиск сессии превращается в join с отдельной логикой на смену
профиля рантайма. Колонки разговора в самой сессии дают ту же гарантию одним
индексом.

**Сессия по строке `purpose = 'conversation_chat:<conversation_id>'`.** Самое
маленькое изменение: пять функций меняют одно выражение. Отвергнута как
ненадёжная: идентичность живёт в тексте, который база не проверяет, — ошибка в
формате или новый код молча заводят вторую сессию и разрывают память агента.
Именно строковый `purpose`, привязанный к задаче, и породил копирование.

**`conversation_entries` — таблица, которая нумерует и домен, и аудит.** План
называет её единственным способом держать один строгий порядок на две таблицы.
Отвергнута, потому что аудит не часть разговора: это запись о действиях над
системой, и на хосте на одно сообщение приходится больше ста его строк. Смешивание
этих двух потоков — ровно то, из-за чего чат опустел. Лента «события и аудит»
остаётся упорядоченной по времени, и это честно: её никто не читает как диалог.

**Минимальная модель без `conversations`** (только уникальные индексы и таблица
связи). План уже отказался от неё: разговор — основная сущность продукта, и без
неё нейтральные задачи и провенанс пришлось бы переделывать после 11.2.

**Счётчик в последовательности PostgreSQL на разговор или `max(sequence)+1`.**
Последовательность не транзакционна: откат оставляет дыру, и «монотонный» номер
перестаёт значить «без пропусков». `max()+1` без блокировки выдаёт один номер двум
писателям. Строка разговора с блокировкой даёт и то и другое.

## Consequences

- Панель строит чат из событий разговора по `conversation_sequence`, без окна
  проекта. Обход родословной в браузере уходит.
- Пять функций, искавших сессию по `purpose`, ищут её по
  `(conversation_id, role, agent_id)`. Смена рантайма посреди разговора — явная:
  прежняя сессия деактивируется, заводится новая, обе остаются в истории.
- Миграция размечает существующие данные: разговор на каждую корневую задачу, номера
  существующим событиям в порядке `occurred_at`, разговор и роль каждой сессии из её
  `purpose`, пространство имён по типу рантайма. Копии нативных сессий, если найдутся, сливаются в
  каноническую строку с записью, какая строка во что слита, — а не падают на
  уникальности посреди обновления. На хосте копий нет: проверено до миграции.
- Supersedes: ничего. Утверждение ARCHITECTURE.md «каждая задача — свой разговор»
  исправляется.
