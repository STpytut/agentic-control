# ADR-0011: Модель доступа self-hosted установки

- Status: Accepted
- Date: 2026-09-10

## Context

Панель переводится в self-hosted режим: клиент запускает installer на своём Ubuntu VPS, получает локальный PostgreSQL, локальную учётную запись и работающую установку, не зависящую от нашей инфраструктуры. Supabase и Vercel уходят.

Текущее состояние делает наивный перенос небезопасным:

- **Ни одной `SECURITY DEFINER` функции.** `grep -ri "security definer" db/` → ноль. `write_audit_event` (`0006_security_recovery.sql:87`) — `SECURITY INVOKER` с закреплённым `search_path`. Любой вызывающий обязан иметь прямые табличные привилегии на всё, что функция трогает.
- **Ни одного `GRANT`/`CREATE ROLE` в 32 миграциях**, кроме `REVOKE ALL ON runtime_health FROM PUBLIC` (`0009:16`). Сегодня всё работает потому, что мигрирующая роль совпадает с подключающейся.
- **Привилегированная FS-операция выполняется из непривилегированного координатора.** `project-provisioner.mjs:103` делает `chown -R codex-poc:agent-workspace`, а юнит работает от `User=codex-poc` (`infra-cod-project-provisioner.service:8`) — проходит только по chgrp-семантике.
- **Пакет `postgresql-17` на чистой Ubuntu создаёт кластер `17/main` на 5432**, а `setup-postgresql-17-restore.sh` требует порт 5433 у того же кластера `17/main` — то есть drill пытался занять пакетный production-кластер, а не отдельный.
- **Номера миграций 0029–0032 зарезервированы** под Sprint 7.2 (`docs/SPRINT_7_2_DESIGN.md:976`), при том что установлены 0033–0036.

Пять решений ниже фиксируются до написания кода, потому что расходятся в setup-скрипт, systemd-юниты, миграции и installer.

## Decision

### 1. Linux-пользователи и DB-роли маппятся строго 1:1

Peer-аутентификация через Unix-сокет; паролей нет. Ни один непривилегированный OS-пользователь не может принять две роли — иначе разделение фиктивно: процесс просто указал бы другой `PGUSER`.

| OS-пользователь | Роль PostgreSQL |
| --- | --- |
| `infra-web` *(новый)* | `infra_web` |
| `infra-control` | `infra_worker` |
| `infra-cod-github` | `infra_worker` |
| `postgres` | `postgres` |
| `root` | `infra_migrator`, `infra_backup`, `infra_worker` |
| `codex-poc`, `opencode-worker`, будущий `claude-*` | доступа к PostgreSQL нет |

`root` — единственное исключение из правила 1:1, и оно не ослабляет границу: root уже может стать любым пользователем через `su`, поэтому отдельная строка в `pg_ident.conf` не даёт ему ничего нового. Три роли ему нужны предметно: `infra_migrator` для DDL из installer'а, `infra_backup` для `pg_dump` из таймера, `infra_worker` для Runtime Supervisor, который обязан быть root'ом (см. решение 3) и при этом ведёт `workspace_operations`.

`postgres → postgres` — не application capability, а сохранение локального
пути администратора самого кластера после установки catch-all peer rule.
Application unit не работает под этим OS-пользователем.

Граница, которую этот пункт действительно защищает, — между двумя **непривилегированными** равными: web-процесс не может стать worker'ом, а runtime-пользователи агентов не имеют доступа к базе ни в каком виде.

`infra-web` — новый OS-пользователь; `infra-cod-web.service` меняет `User=infra-control` на `User=infra-web`.

Доступ только через Unix-сокет: `pg_hba.conf` содержит `local ... peer map=infra_cod_map` и явный `reject` для `host 127.0.0.1/32` и `::1/128`. Во всех юнитах прописывается `PGHOST=/var/run/postgresql`, потому что `PrivateTmp=true` даёт приватный `/tmp` и молчаливый провал при откате на дефолтный сокет.

### 2. `infra_web` не получает DML

Граница web/worker делается настоящей, а не декларативной:

- ~30 функций `control_plane`, уже образующих операторский API (`request_*`, `get_operator_*`, `approve_*`, `decide_*`, `append_event`, `write_audit_event`), переводятся в `SECURITY DEFINER OWNER infra_migrator`. Предпосылка выполнена: у всех закреплён `search_path` по конвенции 0004/0009. Каждая функция при конверсии проходит аудит на самостоятельную проверку владения объектом.
- Прямая DML-поверхность web-слоя — **13 операторов**, а не четыре, как оценивалось изначально: `control-plane-actions.ts:232,242,248,261,267,273` (создание проекта одним CTE), `:425` (retry provisioning), `:463,483` (создание задачи), `:539` (bump версии задачи), `:660` (catalog gate allowlist), плюс `auth.ts:82,88`, которые исчезают вместе с Supabase. Они сворачиваются в пять функций: `create_project_with_roster`, `retry_project_provisioning`, `create_task_with_executors`, `record_task_chat_message`, `request_catalog_gate_allowlist`.
- `infra_web` получает `EXECUTE` на явный список функций и `SELECT`, устроенный так:
  таблицы, целиком состоящие из секретов (`github_oauth_codes`,
  `provider_secret_enrollments`, `credential_references`, `web_sessions`,
  `auth_attempts`), не выдаются вообще; семь таблиц со смешанным содержимым
  выдаются **поколоночно**, без секретного столбца (`users.password_hash`,
  `workspace_locks.fencing_token`, `task_runs.workspace_fencing_token`,
  `worker_completion_reports.fencing_token`,
  `worker_interaction_reports.fencing_token`,
  `runtime_launch_reservations.token`,
  `provider_connections.native_credential_reference`); остальные — на уровне
  таблицы.

  Поколоночная выдача обязательна, а не стилистична: в PostgreSQL **table-level
  `GRANT` перекрывает column-level `REVOKE`**. Проверено на 17.11 — после
  `GRANT SELECT ON t` последующий `REVOKE SELECT (secret) ON t` не блокирует
  чтение `secret`. Поэтому «выдать таблицу и отозвать колонку» не работает;
  единственная рабочая форма — выдавать только разрешённые столбцы.

- **`append_event` и `write_audit_event` намеренно не выдаются `infra_web`.** Обе принимают actor параметром, то есть web-роль могла бы подделать запись аудита или вбросить произвольное outbox-событие. `append_event` из `apps/web` не вызывается вообще. Для операторского аудита есть узкая `write_operator_audit`, которая жёстко ставит `actor_type='operator'`, выводит actor из id пользователя и ограничивает действие пространствами `auth.*` и `operator.*`.

- **`ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` должен быть глобальным, без `IN SCHEMA`.** PostgreSQL выдаёт `EXECUTE` на каждую новую функцию роли `PUBLIC`, и это **глобальная** встроенная привилегия: schema-scoped отзыв её не снимает. Измерено на 17.11 — с `IN SCHEMA` созданная функция получает `proacl = NULL` (владелец + PUBLIC), без него — `{owner=X/owner}`. Поведение соответствует документации PostgreSQL 17. Дополнительно оставлена `assert_no_public_function_execute()` как защита от явного `GRANT ... TO PUBLIC` в будущей миграции: она вызывается из `db/tests/0026` и из `migrate.mjs` **после каждого файла и до записи в ledger**, поэтому протекающая миграция называется по имени, не штампуется как применённая и останавливает прогон.

- `ALTER DEFAULT PRIVILEGES` для `infra_web` намеренно **не** задаётся: каждая новая таблица должна получать доступ явно, иначе граница размоется молча.
- `infra_worker` сохраняет полный DML — он и есть исполнительный слой. Для него `ALTER DEFAULT PRIVILEGES` обязателен, иначе будущая миграция создаст таблицы, которые никто не сможет прочитать, и провал будет молчаливым до рантайма.

### 3. FS-операции provisioning'а выполняет только Runtime Supervisor

- `project-provisioner` работает от `infra-control` без root и делает только координацию: клеймит проект, ведёт состояние, ставит запись в `workspace_operations`.
- `mkdir`, `chown -R`, `chmod -R` и удаление выполняет Runtime Supervisor через уже существующий канал `claim_workspace_operation` / `finish_workspace_operation` (`server.mjs:64,137`). Это не новый привилегированный код, а перенос вызова туда, где он уже реализован под allowlist протокола.
- Пара `(user, group)` для `chown` берётся из allowlist в супервизоре, а не из параметра запроса — иначе появится примитив «chown чего угодно куда угодно». Карта уже введена в `server.mjs`: `codex-poc`/`opencode-worker` → `agent-workspace`, `infra-control` → `infra-control`.
- Runtime Supervisor остаётся root'ом: он меняет владельца чужих файлов и создаёт сокеты с заданными группами.

### 4. Имена кластеров PostgreSQL следуют поведению пакета

- production: `17/main`, порт 5432 — как создаёт пакет;
- restore drill: `17/restore`, порт 5433.

Обратное распределение (production на именованном кластере рядом с пакетным `17/main`) ломалось бы на каждой чистой установке. Разовая правка `setup-postgresql-17-restore.sh` и `infra-cod-restore-drill.service` дешевле, чем борьба с пакетным менеджером при каждой инсталляции.

Отдельный кластер означает отдельный unit: `postgresql@17-restore.service`, а не `postgresql@17-main.service` на другом порту. Роль `infra_control` существует только в restore-кластере и владеет временной базой drill'а; в `17/main` её нет, поэтому пятая production-роль не появляется.

### 5. Резерв номеров миграций 0029–0032 снимается

`migrate.mjs` идёт по отсортированным файлам и применяет всё непроштампованное, поэтому миграция с меньшим номером, выпущенная позже, применится после большего. Фактический порядок на 2026-09-11:

- `0037_local_auth.sql`
- `0038_local_role_privileges.sql`
- `0039_workspace_provisioning_operations.sql` … `0042_release_project_cleanup.sql`
- `0043_local_auth_session_rotation.sql`
- `0044_drop_supabase_auth.sql`
- `0045_local_operator_admin.sql`

Номера выдаются в порядке приземления, а не по плану: провижининг занял `0039` раньше, чем дошла очередь до удаления Supabase, а атомарная ротация сессий и администрирование оператора — раньше, чем `0044`. Это ровно то правило, ради которого снят резерв — миграция с меньшим номером не может выйти после уже применённой большей. Здесь оно сработало в обратную сторону: `0044` планировалась как `0040`, но `0040` был занят, поэтому удаление Supabase переехало на свободный номер, а не переименовало применённый файл.

Baseline-import из `supabase_migrations` удалён вместе с `0044`: доверенного ledger'а больше нет, и база со схемой без ledger'а теперь отвергается, а не догадывается.

`0037` применяется строго до `0038`: гранты ссылаются на таблицы, созданные auth-миграцией.

### Аудит изменений доступа

Две операции меняют доступ и обязаны оставлять след: смена пароля, username,
отзыв сессий и вход — со стороны web, и всё, что делает `infra-cod admin`, — со
стороны CLI.

- **Web.** Изменение и его audit-строка пишутся в одной транзакции
  (`withTransaction` в `apps/web/src/lib/database.ts` и `services/control-plane/db.mjs`).
  Иначе сбой между двумя запросами оставляет либо живую сессию, о которой никто
  не знает, либо запись о том, чего не было: и то и другое хуже, чем отказ.
- **CLI.** База не видит, кто запустил процесс, поэтому `actor_id` формируется
  как `cli:<OS-пользователь>`: `SUDO_USER` (человек, вызвавший `sudo`), иначе
  `INFRA_COD_ACTOR`, иначе имя процесса. Раньше `set_local_operator_disabled`
  писала строку сама, с захардкоженным `system:infra-cod-admin` — такая запись
  выглядит достоверной и потому хуже отсутствующей. Теперь строка приходит из
  CLI, в той же транзакции, что и изменение (0046 убирает внутренний аудит
  функции).

### Жизненный цикл initial-credentials

`bootstrap` в неинтерактивном режиме кладёт сгенерированный пароль в
`/etc/infra-cod/initial-credentials` (0600, root). Это единственный plaintext-секрет,
который система пишет на диск, поэтому удаляется он по строгому условию:
**успешный вход записан в БД И форсированная смена пароля завершена**.
Одного входа мало — файл остаётся единственной копией пароля, и оператор,
вошедший и не сменивший пароль, остался бы без доступа.

Условие считает `initial_credentials_status()` (0046), а не вызывающая сторона:
два независимых вывода разошлись бы, и одна из сторон удалила бы живой пароль.
Удаляет root-owned `infra-cod-health` (таймер `infra-cod-health.timer`), которому
для этого добавлен `ReadWritePaths=/etc/infra-cod`; web-процесс к файлу доступа не
имеет и права голоса не имеет. Вручную — `infra-cod admin ack-credentials
[--if-retired]`.

**Удаление и его аудит не могут быть одной транзакцией** — одно трогает файловую
систему, другое БД. Поэтому операция durable, а не атомарная: таблица
`credential_retirements` (0047) ведёт `requested → file_removed → recorded`, каждый
шаг идемпотентен, а `recorded` терминален и уникален на путь, что и даёт ровно
одну строку аудита. Сбой между `unlink` и записью в `audit_events` не теряется:
следующий запуск видит открытую строку и доводит её до конца. Состояние
`file_removed` при этом не даёт пропустить удаление, если файл появился снова.

`readCredentialsState()` различает три состояния — `exists: true | false | null`,
где `null` значит «прочитать не удалось». Схлопывание ошибки чтения в «файла нет»
и есть способ показать чистую машину при лежащем на диске plaintext-пароле,
поэтому `null` всегда critical alert и никогда не основание для удаления.

### Fence на смену учётных данных

Проверка пароля и выдача сессии — это Argon2id в приложении плюс запись в БД,
и между ними помещается чужая смена состояния. `complete_local_login` (0047)
закрывает окно: одна функция под блокировкой строки пользователя сверяет
`expected_username + expected_password_hash` с тем, что реально лежит в строке,
и только потом резолвит попытку, создаёт сессию и пишет аудит. Порядок перестаёт
быть лотереей: либо смена коммитится первой и вход отказывает, либо вход
коммитится первым и последующая смена отзывает созданную им сессию.

`rehash_local_password` (0047) обновляет кодировку только через compare-and-swap
по `password_hash`. Без него фоновое перехеширование, решённое по устаревшему
хэшу, записывало новую кодировку **старого** пароля поверх только что
сброшенного — то есть отменяло смену учётных данных. Проигранный CAS — не ошибка:
чужая смена важнее, аудит не пишется.

### Grant — это и есть возможность

Удаление вызывающего кода не удаляет привилегию. Когда web-слой перешёл на
узкие token-derived функции (0043/0047), старые grants остались: `infra_web`
по-прежнему мог вызвать `create_web_session(user_id, ...)` и выпустить валидную
сессию без пароля, без попытки входа, без fence и без `auth.login`, а
`set_user_password(user_id, ...)` давал скомпрометированному web-процессу прямую
смену хэша владельца. Компилятор и `grep` по `apps/web/src` этого не видят —
они видят только то, что вызывается, а не то, что *может быть вызвано*.

`0048` отзывает восемь grant'ов: `create_web_session`, `set_user_password`,
`set_user_username`, `revoke_user_sessions`, `record_auth_attempt`,
`request_catalog_verification` и обе перегрузки `capture_task_runtime_snapshot`
(последние три вызываются только изнутри `SECURITY DEFINER` обёрток).
`0026` закрепляет **полный** allowlist исполняемых функций `infra_web` —
50 сигнатур — и проверяет отказы вызовом под `SET ROLE infra_web`, а не только
битом привилегии. Следующее сужение API обязано отозвать старый grant, иначе
тест падает на появлении функции вне списка.

Правило на будущее: поверхность привилегий проверяется по `pg_proc` и
`information_schema`, а не по коду приложения.

### Кто именно пишет аудит

`write_operator_audit` принимала actor параметром и была выдана `infra_web`.
Проверка «такой владелец существует» — это не «вызывающий и есть этот владелец»,
и на глаз эти две проверки неотличимы: комментарий в 0038 утверждал, что подделать
запись нельзя, а под `SET ROLE infra_web` проходил `auth.login` с actor'ом
владельца и произвольными session id и details.

Разделены два разных повода писать аудит:

- **События об учётных данных** — вход, смена пароля, переименование, отзыв сессий,
  logout — пишет та же `SECURITY DEFINER` функция, что выполнила изменение: она уже
  знает аккаунт из предъявленного токена. Web-слой не передаёт user id вообще.
- **Действия оператора** (`operator.*`) — единственное, что web-слой порождает сам.
  `write_session_audit` (0049) принимает digest сессии и выводит actor из строки
  сессии, поэтому назвать чужой аккаунт нечем: максимум для скомпрометированного
  web-процесса — приписать действие сессии, которую он и так держит.

`write_operator_audit` остаётся внутренней: её вызывает `complete_local_login`, и
это правильная форма для definer-функции, которая актора уже установила. Убран
только grant, а полный allowlist в 0026 держит его убранным.

`write_session_audit` пишет **только `operator.*`** (0050). Привязки актора к
живой сессии недостаточно: она мешает выдать один аккаунт за другой, но
`auth.password_changed` без смены пароля и `auth.login` без входа — всё ещё
ложь, независимо от того, чьей сессией она подписана. События об учётных данных
пишут только те функции, которые выполнили операцию.

### Единственная транзакция в web-слое

Control-plane действие и строка «оператор это запросил» — одна транзакция.
Разделённые, они давали худший из отказов: изменение применено, записи о том,
кто просил, нет, а вызывающему сказано «ошибка» — то есть повтор создаёт
дубликат или конфликт.

Диспетчеризация действий живёт в TypeScript (три десятка `executeJson`), поэтому
обернуть каждое действие в SQL значило бы продублировать её. Вместо этого
`withTransaction` (`apps/web/src/lib/database.ts`) кладёт соединение в
`AsyncLocalStorage`, и все query-хелперы его читают: код внутри обработчика
попадает в транзакцию, даже если ничего о ней не знает. Два следствия, которые
надо помнить: транзакция держится на всё время обработчика, поэтому внутри нельзя
делать медленную не-DB работу; вложенный `withTransaction` присоединяется к
внешней.

Отказ пишется **вне** транзакции: она уже откатилась, а отказ — ровно то, что
обязано пережить откат. Проверяется инъекцией отказа
(`action-atomicity.test.mjs`): функция аудита подменяется на бросающую исключение,
и утверждается не только код ответа, но и что строка в БД не изменилась.

Удалён только `createSession`. Он выдавал сессию по одному `user_id` и пережил
бы появление настоящей проверки пароля: вход идёт через `complete_local_login`,
смена пароля — через `change_local_password`, и третий экспортированный вход в
жизненный цикл сессии приглашал бы вернуть гонку, которую закрыл 0047.
`withTransaction` остаётся и применяется: это единственный способ, которым
dispatch действия в TypeScript и его `operator.*`-строка аудита попадают в одну
транзакцию.

Механизм проверяется отдельно от product path. `action-atomicity.test.mjs`
покрывает сквозной путь и инъекцию отказа; `transaction-context.test.mjs`
проверяет сам `apps/web/src/lib/database.ts` на отдельной временной БД: два
параллельных `withTransaction` получают разные backend'ы и не видят
незакоммиченных записей друг друга, вложенный вызов идёт по внешнему соединению и
откатывается вместе с ним, исключение после нескольких `executeJson` откатывает
все операторы, а запрос после выхода из scope выполняется в autocommit через pool.

## Consequences
- Installer обязан создавать OS-пользователя `infra-web` до первого запуска web.
- Работа по грантам — это миграция, а не конфиг: конверсия 37 функций (36 имён, у `capture_task_runtime_snapshot` две перегрузки) плюс пять новых. Регрессионная сеть — `npm run db:test` под `infra_worker` и отдельный прогон web-сценариев под `infra_web`, плюс обязательный негативный набор (`INSERT`/`UPDATE`/`DELETE` под `infra_web` → permission denied; `infra-web` не может стать `infra_worker`).
- **Решение 3 нельзя применить одним изменением `User=`, и это отдельный подэтап.** Сегодня Runtime Supervisor принимает только `recover_lock` и `restore_owner` (`server.mjs:105`), и констрейнт БД на `workspace_operations` разрешает те же две операции. Пока провижининга в протоколе нет, смена `User=codex-poc` на `infra-control` просто сломает прямой `chown` в `project-provisioner.mjs:103`. Порядок обязателен:

  1. новые типы операций `provision_workspace` и `inspect_workspace` — в констрейнте БД и в протоколе супервизора;
  2. allowlist путей, владельцев и групп для них (пара `(user, group)` берётся из карты в супервизоре, а не из запроса);
  3. `project-provisioner` переводится на координацию: ставит операцию и ждёт её завершения;
  4. привилегированные FS- и git-операции переезжают в супервизор;
  5. только после этого `User=infra-control` и удаление `codex-poc` из `pg_ident.conf`.

  Пункты 1–4 — предпосылка Этапа 2, а не его следствие.

- `project-provisioner` теряет прямые FS-вызовы; путь становится асинхронным через `workspace_operations`, что добавляет ожидание завершения операции в его цикл.
- `DATABASE_URL` перестаёт существовать в production. Он остаётся dev/CI-only override: `db/tests/*.sql`, `launch-admission.test.mjs` и `gate-quota-concurrency.test.mjs` продолжают работать через psql.
- Требуется обновить `docs/SPRINT_7_2_DESIGN.md:976` и `docs/SPRINT_7_1_PLAN.md:263`, где резерв 0029–0032 зафиксирован.
- Разделение `infra_web`/`infra_worker` осмысленно только вместе с решением 2: без конверсии в `SECURITY DEFINER` две роли пришлось бы наделить одинаковым DML, и разделение было бы декоративным.

### Транзакции миграций

Миграции `0001`–`0038` открывают и закрывают собственную транзакцию, поэтому раннер не может обернуть их: их `COMMIT` завершил бы внешнюю транзакцию досрочно. Переписать их нельзя — их контрольные суммы записаны в ledger уже развёрнутых установок.

**Начиная с `0039` конвенция обратная: файл миграции не содержит `BEGIN`/`COMMIT`, транзакцией владеет раннер.** Только так применение DDL, проверка инвариантов и запись в ledger становятся атомарными: при провале проверки откатывается всё, включая созданные объекты. `migrate.mjs` отказывается запускать миграцию после `0038`, которая управляет транзакцией сама, — и делает это до применения чего-либо.

Остаточный риск ограничен 34 legacy-файлами: для них провалившаяся проверка не может отменить уже закоммиченный файл, гарантируется лишь что он не попадёт в ledger и прогон остановится. Все они сегодня проходят проверку.

### Результат аудита функций

Аудит 37 операторских функций дал чёткое разделение:

- **25** принимают `p_owner_id`/`p_operator_id` и скоупятся по нему (`WHERE owner_id=p_owner_id`);
- **12** не проверяют владение вообще: `append_event`, `write_audit_event`, `approve_task_review`, `create_followup_task`, `request_revision`, `request_runtime_interrupt`, `request_workspace_operation`, `decide_approval`, `resolve_runtime_job_incident`, `resolve_worker_interaction` и обе перегрузки `capture_task_runtime_snapshot`.

Существенное уточнение, которое меняет трактовку этих двенадцати: **база не может аутентифицировать оператора**. Для всех операторских действий `session_user` — это `infra_web`, а не человек. Поэтому проверка по `p_owner_id` в первых двадцати пяти — это проверка *консистентности* (объект принадлежит заявленному владельцу), а не аутентификация; аутентификация целиком живёт в серверной сессии приложения (решение из `0037`).

Отсюда: конверсия всех 37 в `SECURITY DEFINER` не ослабляет ничего — сегодня `infra_web` и так обладает полным DML, — а ограничение грантов строго усиливает границу. Двенадцать нескоупленных функций не эксплуатируемы, пока владелец ровно один, что удерживается констрейнтом `users_role_check CHECK (role = 'owner')`.

Эта зависимость фиксируется тестом: `db/tests` утверждает, что `users_role_check` допускает только `owner`. Если кто-то когда-нибудь ослабит констрейнт ради нескольких операторов, тест упадёт и заставит вернуться к этим двенадцати функциям, вместо того чтобы дефект проявился как тихая утечка между операторами.
