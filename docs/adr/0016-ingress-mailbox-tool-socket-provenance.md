# ADR-0016: Два канала к агенту, сокет инструментов на прогон, происхождение запуска

- Status: Accepted
- Date: 2026-09-24
- Stage: 11.1b, WP-9 (миграции `0070`, `0071`)
- Уточняет: [ADR-0013](0013-every-native-turn-is-a-run.md) (ход — это Run; теперь
  у Run есть ящик команд), [ADR-0014](0014-conversation-task-session-run.md)
  (порядок разговора теперь решает и то, когда стартует следующий Run)

## Context

Три вещи, которые до WP-9 были неявными ([STAGE_11_2_PREWORK.md](../STAGE_11_2_PREWORK.md)
A4, A6, A7):

- **Сообщение агенту имело один путь для двух разных вещей.** Новое сообщение
  оркестратору, хэндофф исполнителю и resume после ответа оператора *создают*
  прогон. Ответ на структурный запрос, steer и interrupt — команды *идущему*
  прогону. Прерывание было флагом `interrupt_requested_at` на задании, который
  воркер опрашивал, и никто не записывал, что ответил рантайм. Claim упорядочивал
  задания только внутри одной задачи и по id: реализация стартовала, пока ход,
  делегировавший её, ещё читал дерево.
- **Транспорт инструментов исполнителя был групповым.** Один
  `/run/infra-cod/worker-tools.sock`, 0660, группа `opencode-worker`. Capability
  уже была на прогон, а транспорт — на группу: третий рантайм не мог его
  достичь, а расширение группы дало бы каждому аккаунту рантайма путь к каналу
  каждого прогона.
- **Панель угадывала, что запускалось.** Usage — `CASE WHEN job_type=... THEN
  'opencode' ELSE 'codex'`, кнопка «Stop run» — `runtime_profiles.capabilities`,
  хэндофф — всегда «Codex delegated implementation to OpenCode.». На rc.38 у
  работающего хода Codex не было кнопки: строка профиля не говорила `interrupt`,
  а драйвер Codex объявляет его в обязательном ядре.

## Decision

### 1. Ingress разговора и ящик команд прогона — два канала

**Ingress** (`conversation_ingress`): одна строка на задание, созданное из события
разговора, с `conversation_sequence` этого события. Пишет триггер на
`runtime_jobs` (урок 0063: номер, который пишет одна функция, пропускает любой
другой путь вставки). Вид — `orchestrator_message`, `handoff` или `resume`
(хэндофф, который `resolve_worker_interaction` пишет после ответа оператора).

Оба claim берут задание, только если ни один другой прогон его разговора не
идёт и ни одна более ранняя запись не ждёт (`ingress_blocker`). Сообщение,
набранное во время живого прогона, — новое задание, новый Run *после* него, и
никогда не запись в живой. Dead letter разговор не держит: это дело оператора, а
очередь, ждущая dead letter вечно, — тихая потеря.

**Ящик команд** (`run_commands`): `run_id + sequence + command_kind +
idempotency_key`, виды `input_response`, `steer`, `interrupt`, состояния
`pending → delivering → acknowledged | outcome_unknown | failed`.
`acknowledged` — только с `native_receipt`, тем, что ответил рантайм
(`turn/interrupt` для Codex; завершение группы процессов для OpenCode).
Доставка, которая могла дойти и ответ которой не пришёл, — `outcome_unknown`, не
`failed` (дефекты 47 и 49). Прогон, закончившийся с недоставленными командами,
закрывает их: `pending` → `failed` (`run_command_run_ended`), `delivering` →
`outcome_unknown`; так же — смена аренды задания.

Доставляет держатель аренды задания: воркер Codex для хода, супервизор для
прогона OpenCode. Вид, которого драйвер прогона не объявляет (`input.steer`,
`input.respond` — ни один из двух нынешних драйверов их не имеет), завершается
`run_command_unsupported` и никогда не превращается в новый промпт: это заменило
бы сессию агента. Ответ на вопрос исполнителя остаётся явным interrupt + native
resume: это ingress вида `resume`, новый прогон в той же сессии (`--session`).

`request_runtime_interrupt` (кнопка «Stop run») пишет команду в ящик, продолжает
ставить `interrupt_requested_at` для воркеров предыдущего релиза и не спрашивает
`runtime_profiles`. Прерывание, пришедшее между claim реализации и стартом её
прогона, хранится на задании и становится командой прогона при старте.

### 2. Сокет инструментов на прогон, принадлежащий аккаунту прогона

`/run/infra-cod/worker-tools/<run id>/tools.sock`: каталоги root 0711, сокет
принадлежит аккаунту рантайма прогона, группа root, 0600. `connect()` любого
другого аккаунта ядро отвергает с `EACCES` до первого байта.

Выбран этот вариант плана, а не `SO_PEERCRED`: у Node нет API для учётных данных
пира без нативного модуля, а владелец и режим файла — граница ядра, которую можно
проверить тестом от настоящих пользователей. За режимом — ещё три проверки: при
каждом accept сокет перечитывается (аккаунт владеет inode и мог бы сделать
`chmod`), capability сравнивается с capability этого прогона за постоянное время,
принятый терминальный отчёт её расходует.

Сокет удаляется в том же `finally`, что возвращает каталог, как бы прогон ни
кончился; открытые соединения при этом рвутся (иначе процесс, переживший прогон,
держал бы его конец вечно). Каталоги, оставшиеся от умершего супервизора,
убираются при старте и раз в минуту; `doctor` называет сокет, который никто не
слушает.

### 3. Происхождение: выбор пишется один раз, каждый запуск дописывается

`runtime_job_selections` — первый запуск задания записывает назначение, режим
доступа и grant (из grant прогона), рантайм (из назначения), сессию (из прогона)
и то, что знает только запускающий: версии адаптера и рантайма, верификацию,
объявленные драйвером возможности целиком. Ретрай использует ту же строку. Запуск
для другого назначения, рантайма или режима отвергается
(`runtime_selection_changed`); рантайм, сменивший версию между попытками,
*замещает* выбор строкой, называющей старую и что изменилось. Выбор никогда не
обновляется.

`runtime_dispatch_attempts` — одна строка на каждый реальный запуск: выбор,
номер попытки, прогон, драйвер и исполняемый файл, версии, верификация, сессия,
grant и режим, воркер; один раз, в конце, — native result.

Панель читает это: «Stop run» — `runtime_job_can_interrupt` (объявляет ли
записанный драйвер `interrupt`), тот же ответ, что у `request_runtime_interrupt`;
usage — `conversation_runtime_usage` (токены — по рантайму, чьи шаги их
сообщили, попытки — по выбору задания); хэндофф называет агентов хэндоффа и
рантайм, который запуск реально выполнил. `product-data.ts` не называет ни одного
рантайма: роли для выбора берутся из `runtime-labels.ts`, который тест держит
равным реестру.

## Consequences

- Порядок разговора теперь строже: реализация ждёт окончания хода, который её
  делегировал, ревью — окончания задания реализации. Фикстура 0034, оставлявшая
  задание исполнителя `in_flight` после конца его прогона, дополнена его
  завершением.
- Карточка активности выбирает идущее задание раньше ожидающего: при ingress
  ожидающее сообщение во время прогона — штатный случай, и прежний порядок прятал
  кнопку Stop ровно на время прогона.
- Задания, запущенные предыдущим релизом, имеют только backfill-выбор без
  возможностей: для них кнопка Stop не показывается, а `request_runtime_interrupt`
  их не отвергает.
- Членство `infra-control` в группе `opencode-worker` больше не нужно для сокета
  инструментов; оно остаётся и проверяется, пока не выяснено, нужно ли оно чему-то
  ещё.
- 11.2 получает оба канала и происхождение готовыми: нейтральные job types
  меняют только то, как задание выбирает драйвер, а не то, как в него приходит
  команда и как записывается, что запустилось.
