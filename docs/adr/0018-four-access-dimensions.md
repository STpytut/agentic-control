# ADR-0018: Runtime, производитель модели, шлюз доступа и учётные данные — четыре разных измерения

- Status: Accepted (owner, 2026-09-26)
- Date: 2026-09-26
- Stage: 11.4 и путь публикации, спринт B (пакеты A2–A4, P1; миграции `0082`–`0086`)
- Решения владельца: B5–B8 в [STAGE_11_SPRINT_B_PLAN.md](../STAGE_11_SPRINT_B_PLAN.md) §3
- Уточняет: [ADR-0004](0004-agent-runtime-provider-model.md) (Agent, Runtime, Provider, Model),
  [ADR-0015](0015-review-evidence-and-publish-boundary.md) (граница публикации)

## Context

На rc.48 один `provider_connections` несёт сразу всё:

- кто запускает (runtime);
- через кого идёт трафик (`provider_id`: `opencode`, `opencode-go`, `openrouter`, `chatgpt`);
- кто платит (`billing_boundary`: `free`, `go`, `external_api`, `chatgpt_subscription` — это названия тарифов, а не смысл);
- чем аутентифицироваться.

В той же таблице лежит GitHub, хотя установка GitHub App — не доступ к моделям. Производитель модели существует только внутри её id (`openai/gpt-6-luna`).

rc.46–rc.47 показали цену этого смешения. Шлюз угадывался по косой черте в id модели, и проверка модели запускала `openai/gpt-6-luna` у провайдера, в который никто не входил.

## Decision

### 1. Четыре измерения

| Измерение | Что это | Где живёт |
| --- | --- | --- |
| Runtime adapter | исполняемый файл и протокол: Codex, OpenCode, Claude Code | реестр адаптеров и драйвер (не данные) |
| Model vendor | автор модели: OpenAI, Anthropic, Z.ai… | `provider_model_catalog.model_vendor` |
| Access gateway | путь трафика и сторона, которая выставляет счёт: `opencode_zen`, `openrouter`, `openai_direct`… | `provider_model_catalog.access_gateway` |
| Credential connection | учётные данные владельца для этого шлюза | строка подключения вида `model_access` |

### 2. Подключения GitHub и доступа к моделям не пересекаются (B6)

- `provider_connections.connection_kind ∈ {scm, model_access}` с раздельными CHECK: у `scm` есть установка и выбор репозиториев, у `model_access` есть runtime, шлюз и способ входа.
- Функции разделены по виду. Каталог, проверка моделей и снимки принимают только `model_access`. Worker GitHub и создание проекта принимают только `scm`.
- id подключения не того вида база отвергает с причиной, и это верно в обе стороны.

Отдельная таблица — запасной путь, если раздельные CHECK станут нечитаемыми. Внешние ключи каталога, снимков и доступов тогда не меняются.

### 3. Оплата — смысл, а не тариф (B7)

`billing_boundary ∈ {free, subscription, direct_metered, third_party_metered}`:

| Было | Стало |
| --- | --- |
| `free` | `free` |
| `go`, `chatgpt_subscription` | `subscription` |
| `external_api` | `third_party_metered` |

«Go», «Plus», «OpenRouter» — отображаемые метаданные каталога. Переход идёт через expand и contract (A3 → `0085`).

### 4. Проверка модели привязана к шлюзу (B8)

Идентичность проверки состоит из:

- подключения;
- шлюза;
- производителя;
- id модели;
- версии адаптера;
- версии runtime.

Одна и та же модель через два шлюза — это две записи каталога и две проверки. Проверка через один шлюз никогда не разрешает модель через другой.

### 5. Отзыв доступа между показом в панели и запуском

- Снимок задачи хранит id подключения и никогда не хранит секрет.
- При dispatch подключение модели из снимка перепроверяется в транзакции claim (A4).
- Если подключение отозвано, просрочено или отключено, задание уходит в dead letter с причиной `model_access_revoked`. Блокировка освобождается, карточка задачи называет причину.
- Утёкших заданий и висящих блокировок нет, в любом порядке событий.

### 6. Публикацию выполняет супервизор токеном установки GitHub App (B5)

- **Намерение.** Одобрение оператором подготовленной публикации создаёт `publish_intent`. Модель его не создаёт никогда (ADR-0017 §7).
- **Операция супервизора:**
  1. выпускает токен установки на один репозиторий проекта (`contents: write`, `pull_requests: write`), живущий одну операцию;
  2. пушит `head_commit_sha` подготовленной строки в ветку, названную по задаче;
  3. открывает PR с итогом ревью;
  4. пишет квитанции (ref ветки, номер и URL PR) событиями.
- **Токен** передаётся через stdin/askpass и никогда не попадает в argv, базу, события или логи. git не выполняется от root (ADR-0015 §4).
- **Отказы:** голова, сдвинувшаяся со времени подготовки, отвергается с названием ref; упавший push повторяется из панели.
- **Какие проекты:** проекты с deploy key и пустые workspace остаются только с подготовкой.
- **Права GitHub App** расширяет владелец. Каждая установка их принимает; до этого операция отказывает с понятной причиной.

## Consequences

- Критерий 9 Stage 11 выполняется схемой, а не соглашением.
- Панель показывает производителя, шлюз и оплату тремя фактами, а не одним значком «OpenCode».
- Критерий 5 — PR, созданный платформой, — становится проверяемым на хосте.
- Нужно одно действие владельца вне кода: права GitHub App.

## Rejected alternatives

- **Универсальная таблица провайдеров с расширенным enum.** Именно она смешала GitHub с доступом к моделям.
- **Угадывать шлюз по id модели.** Дефект rc.46.
- **Push от учётной записи оператора или через deploy key.** Секрет живёт дольше операции, и его область шире одного репозитория.
- **Push моделью.** Полномочие вышло бы из свободного текста модели.
